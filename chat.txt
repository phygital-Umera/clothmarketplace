--------------------------------------------------------------------------
2. CRITICAL
--------------------------------------------------------------------------
C1. Anyone can register as SUPERADMIN
    File : backend/src/routes/user.routes.ts:23 + validations/user.validation.ts:14
    Steps: POST /api/v1/users/register  { ..., "role": "SUPERADMIN" }
    Result: A public, unauthenticated endpoint takes `role` from the request
            body and saves it.
    Expect: Public signup must never set the role. Remove `role` from the
            public schema, or protect the route with checkSuperAdmin.

C2. Register response leaks the password hash and other secrets
    File : backend/src/controllers/user.controller.ts:43, services/user.service.ts:127,139
    Steps: Register a new user, then read the response body.
    Result: The full Prisma User row is returned, including password (bcrypt
            hash), refreshToken, verifyCode and verifyCodeExpiry.
    Expect: Return a safe subset (id, fullname, email, phoneNumber, role).
            utils/exclude.ts already exists for this.

C3. A refresh token also works as an access token
    File : backend/src/services/token.service.ts:37-46, middlewares/auth.middleware.ts:35
    Result: Both tokens are signed with the same JWT_SECRET, and verifyJWT only
            checks `id`. A 30-day refresh token can call every private route.
    Expect: Use a separate secret, or add a `type` claim and reject refresh
            tokens in verifyJWT.

C4. Path traversal in uploaded file names
    File : backend/src/middlewares/multer.middleware.ts:28
    Result: The filename is `${Date.now()}-${file.originalname}`, and the client
            controls originalname. A name like "../../src/x.js" can write
            outside public/temp.
    Expect: Use path.basename(), or a random name plus the checked extension.

--------------------------------------------------------------------------
3. HIGH
--------------------------------------------------------------------------
H1. Registering with no `role` creates a user who can never log in
    File : backend/src/services/user.service.ts:88-90
    Result: The role defaults to ADMIN (`role ?? Role.ADMIN`), but the Admin
            row is only created when `role === 'ADMIN'` was sent explicitly.
            Login then fails with 404 "Admin not found", and verifyJWT fails
            with 401.
    Expect: Check the resolved role, not the raw input.

H2. Login lookup can match the wrong user
    File : backend/src/services/user.service.ts:178
    Result: The query is `OR: [{phoneNumber: username}, {email}]`. One of the
            two is always undefined, and Prisma treats an undefined filter as
            empty. Depending on the Prisma version, this can return an
            arbitrary first user, so real users get "Invalid credentials".
            The `username` field is also compared against phoneNumber.
            NEEDS LIVE CONFIRMATION.
    Expect: Build the where-clause only from fields that were actually sent.

H3. The login rate limiter is never applied
    File : backend/src/app.ts:47
    Result: The limiter is mounted on '/v1/auth', but the routes live at
            '/api/v1/users/*'. Login is open to brute force.
            'trust proxy' = true also lets a client spoof its IP through the
            X-Forwarded-For header.

H4. Fake success on verify-code and reset-password-request
    File : backend/src/services/user.service.ts:254-280
    Result: Both are stubs that only console.log. The API still replies
            "Account verified successfully!" and "Password reset email sent".
    Expect: Implement them, or return 501 Not Implemented.

H5. /reset-password changes the password without the current password
    File : backend/src/routes/user.routes.ts:46
    Result: Any valid access token (or refresh token, see C3) can set a new
            password. That is account takeover if a token is stolen.

H6. The frontend calls backend routes that do not exist
    Frontend (lib/api/Auth/auth.ts, utils/axios.ts)   Backend
    /users/refresh-token                     ->  /users/refresh      (404)
    /users/current-user                      ->  /users/me           (404)
    /users/update-account                    ->  /users/update       (404)
    /notifications, /showDishById/:id,
    cateror/cateror/notification/:id         ->  do not exist        (404)
    Impact: When the access token expires (30 min), the refresh call fails,
            the token is removed, and the user is silently logged out.

H7. Token refresh reads the wrong response shape
    File : frontend/src/utils/axios.ts:44-51
    Result: It reads res.data.accessToken, but the backend wraps the payload as
            { statusCode, data: { accessToken, refreshToken }, ... }.
            Even after H6 is fixed, this stores `undefined` tokens.
    Expect: res.data.data.accessToken

--------------------------------------------------------------------------
4. MEDIUM
--------------------------------------------------------------------------
M1. No route guard: /dashboard opens without logging in.
    frontend/src/layouts/AppLayout.tsx reads isAuthenticated (and imports
    Navigate) but never uses them.
M2. Sign In and Sign Up pages are empty placeholders
    (frontend/src/pages/Signin.tsx, Signup.tsx), so the app cannot be used end
    to end through the UI.
M3. Super admin is never detected: AuthContextProvider.tsx:33 compares
    role === 'SuperAdmin', but the backend sends 'SUPERADMIN'.
M4. Frontend login only treats '@gmail.com' addresses as emails
    (lib/api/Auth/auth.ts:53). Any other email is sent as `username`, which
    the backend compares against phoneNumber, so login fails.
M5. PATCH /users/update returns 500 for many valid-looking inputs
    (user.validation.ts:90). updateUserSchema allows fields that are not on the
    User model (dob, customerLimit, city, amount, contactPerson*, ...), and
    prisma.user.update rejects them with a validation error.
M6. 404 handler double response: middlewares/error.middleware.ts:10-13 sends a
    response and then calls next(error), so errorHandler tries to respond again.
    Result: "Cannot set headers after they are sent" on every unknown URL.
M7. CORS is origin '*' with credentials:true, and the CORS_ORIGINS env is
    ignored. Browsers block credentialed requests with '*', and the cookies are
    `secure:true` while the frontend uses plain http://192.168.x.x, so the
    cookies are never set.
M8. Logout cannot complete when the backend is down: DropdownUser.tsx:16. If
    logoutUser() throws, the localStorage cleanup and reload never run.

--------------------------------------------------------------------------
5. LOW / CLEAN-UP
--------------------------------------------------------------------------
L1. Uploaded temp files in public/temp are never deleted. The disk fills up
    over time. public/ is also served statically, so temp uploads are publicly
    downloadable.
L2. The upload whitelist accepts video, audio and Office files for `logo` and
    `coverImage`. Limit these to images.
L3. The XSS middleware is disabled (app.ts:28, TODO).
L4. 500 responses return raw internal error messages, and the error handler
    console.logs every error twice.
L5. A user without a password (created by the getUserInfo sync) makes login
    call bcrypt.compare(undefined) and fail with a 500 instead of a 401.
    About 270 frontend component files are leftover catering-app code that no
    route uses (package name "caterringmanagement", backend name "restaurant").
